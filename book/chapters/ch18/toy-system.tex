\section{A Toy Encrypted Search System}
\label{sec:toy-system}

This section turns the framing into the smallest running form that
exhibits every piece of the framework: a single-client, single-server,
per-document Bloom system with a symmetric cipher for the index and a
keyed function for the query tokens. It is deliberately minimal, handling
no multi-user key management, no index rotation, and no side-channel
defense beyond the primitives' standard guarantees; what it does is show
the cipher-map abstraction in operational form, the client encrypting
something, the server operating on the ciphertext to return an approximate
answer, and the framework pricing the recovery-leakage trade-off at every
stage. The companion notebook materializes it; the prose gives the
structure the notebook fills.

\subsection*{Construction, setup, and query}

Three cryptographic ingredients suffice: a keyed function
$\mathrm{HMAC}_k$ producing a query token $\tau_w = \mathrm{HMAC}_k(w)$,
deterministic in $w$ and pseudorandom to anyone without $k$; a symmetric
cipher (AES-based in practice) for the bit arrays; and the Bloom
filter of \Cref{def:bloom-filter} as the per-document structure.\index{encrypted search} Each
document's keyword set becomes a filter $B_i$, encrypted as
$\mathsf{Enc}(B_i)$ and uploaded with its identifier; the client keeps both
keys, the server keeps the encrypted store, and neither party holds both
the plaintext keywords and the bits they hash to. The match operation is
the cipher map: to test whether $\tau_w$ corresponds to a keyword in
$d_i$, the server checks whether the bit positions $\tau_w$ addresses are
all set in the recovered filter, reporting $\top$ (``$d_i$ may contain the
keyword'') or $\bot$ (``$d_i$ definitely does not,'' by $\fnrate = 0$).
The simplest variant decrypts the filter server-side, a security
regression that production variants avoid with bilinear pairings or
one-time-pad-keyed arrays at extra cost; for the toy system the
simplification is acceptable.

Setup runs once per corpus on the client: for each document, extract the
keyword set, build a filter at the target $\fprate$ (the chapter 5 size
$m \approx 1.44\,W_d \log_2(1/\fprate)$), encrypt, upload. A query is a
two-round-trip protocol: the client computes $\tau_w$ locally and sends
it, the server matches it against every encrypted filter and returns the
matched identifiers, and the client verifies the candidates (by a
second-pass decryption outside the encrypted-search layer) and discards
the false positives. The server never sees the plaintext keyword (the
HMAC hides it), the plaintext keyword set (the filter hides it up to false
positives), or the verification step (entirely client-side). What it sees
is the cipher-map output stream chapter 17 predicted, which the chapter 7
PPV prices.

\subsection*{Trace through a single query}

Query \texttt{alice} against $|D| = 1000$ documents at $\fprate = 0.01$,
$\fnrate = 0$, with true match set $\{17, 209, 832\}$. The client computes
$\tau_{\mathrm{alice}}$, a fixed-size pseudorandom string; the rates enter
through the filter parameters fixed at setup, and the prevalence is $\pi =
3/1000 = 0.003$. The server tests the token against all 1000 filters: the
three true matches return $\top$ unconditionally ($\fnrate = 0$), and the
997 non-matches return $\top$ at rate $0.01$, an expected $9.97$ false
positives, for a reported set of about $13$. The client decrypts the
candidates, confirms the three, and discards the rest. The query's PPV is
\[
  \PPV = \frac{0.003}{0.003 + 0.997 \cdot 0.01} \approx \frac{0.003}{0.01297}
  \approx 0.231, \qquad C \approx 0.769,
\]
the matches dominated by false positives and the confidentiality margin
correspondingly large. The trace exhibits every framework parameter in
operational form, each predicted before the trace ran.

\subsection*{Tuning for privacy}

The toy system as built is correctness-tuned. A production trace at a
higher prevalence $\pi = 0.1$ (queried keywords are \emph{interesting}
keywords) with $\fprate = 0.01$ gives $\PPV \approx 0.917$, $C \approx
0.083$: an observer who sees a match for a document holds a $92\%$
posterior that the queried keyword really occurs in it. Retuning is mechanical:
solving the chapter 7 PPV equation, $\fprate^* = \pi C / [(1 - \pi)(1 -
C)]$, a target $C = 0.5$ at $\pi = 0.1$ needs $\fprate^* = 0.05/0.45
\approx 0.111$. The filter shrinks correspondingly, $m \approx 1.44 \cdot
10 \cdot \log_2(9) \approx 46$ bits against $96$ at $\fprate = 0.01$, and
the client's post-filtering load grows. Within this construction no choice escapes the trade-off; the design
freedom is which point of the space, accuracy, and cover triangle to
occupy.

\begin{remark}[The framework as a design language]
\label{rem:design-language}
The three budgets of an encrypted-search deployment each have a price the
framework reads off a different chapter. A \emph{privacy} budget, a target
confidentiality $C^*$, fixes the false-positive rate through the chapter 7
posterior, $\fprate \ge \pi C^* / [(1 - \pi)(1 - C^*)]$. A \emph{correctness}
budget, a cap $B$ on expected false positives per query over a corpus of
$|D|$ documents, fixes it from the other side, $\fprate \le B/|D|$. A
\emph{storage} budget caps the bits through the chapter 5 and chapter 8
space law, $1.44\,|D|\,W_d \log_2(1/\fprate) \le S$, a lower bound on
$\fprate$. The three constraints carve a feasible interval for $\fprate$
at a given $\pi$, and the design rule reads the operating point off it, or
reports that no feasible point exists when the privacy floor exceeds the
correctness ceiling, as happens when a high $C^*$ is demanded at a high
prevalence (the $\fprate^* = 1$ degeneracy of \Cref{sec:confidentiality-measures}).
The same triangle priced chapters 6, 7, 8, 14, and 17; the encrypted-search
designer solves it as one system of inequalities.
\end{remark}

The companion notebook implements the toy system end-to-end on a
synthetic corpus; it is the file \texttt{ch18-encrypted-search.ipynb} in

starting point, not a production artifact; a real deployment should
consult the SSE literature and the primitives' formal security
definitions, which the notebook does not engage.\par}
