\section{Space and Time Analysis}
\label{sec:space-time-analysis}

The BPHF stores the minimal perfect hash $\phi$ and the rank table $R$ of
width $r = \lceil \log_2 n \rceil$. This section totals the bits, gives
the build and query times the construction inherits from the perfect hash
filter, and tabulates the trade against it. The headline is
\Cref{prop:bphf-space}: the per-element cost is $\lceil \log_2 n \rceil$
for the ranks plus the perfect hash's addressing cost, which is at least
$\log_2 e$. The build is expected $O(n)$ and queries $O(1)$, as for the
perfect hash filter. The structural difference is on the space axis: the
BPHF's bits per element grow with the set size $n$, the perfect hash
filter's with the target precision $\log_2(1/\fprate)$, so the two are
not substitutes parameter for parameter.

\subsection*{Rank table storage}

The table $R : [n] \to \{0, 1\}^r$ holds $n$ slots of $r$ bits, so
\begin{equation}
\label{eq:bphf-rank-bits}
  L_R \;=\; n \cdot r \;=\; n \cdot \lceil \log_2 n \rceil
\end{equation}
bits, growing as $n \log_2 n$, the cost any index pays to distinguish
$n$ ranks. At $n = 10^6$ the table is $20 \cdot 10^6$ bits, about $2.5$
megabytes; at $n = 10^9$ it is $30 \cdot 10^9$ bits, about $3.75$
gigabytes. The integer rounding in $r$ adds between $0$ and $1$ bits per
element over $\log_2 n$, as it does for fingerprints in the perfect hash
filter.

\subsection*{Perfect-hash storage}

The perfect hash depends on the set, not on the values stored at each
slot, so the BPHF inherits the perfect hash filter's addressing cost
unchanged: $L_\phi \ge n \log_2 e - O(\log n)$ bits for any minimal
perfect hash function\index{space lower bound!minimal perfect hashing}\index{minimal perfect hash function} \parencite{fredman-komlos-1984}, and in practice
from about $1.5$ bits per key (RecSplit, ShockHash) to about $3$ (BBHash),
with hash-displace-and-compress near $2$ (\Cref{prop:phf-space}). The
rank pass populates $R[\phi(a)] = \rho(a)$ where the perfect hash filter
populated $F[\phi(a)] = g(a)$; the representation, slot count, and
addressing are identical.

\subsection*{Total bits per element}

Combining,
\begin{equation}
\label{eq:bphf-total-bits}
  L_{\text{BPHF}}
  \;=\; L_R + L_\phi
  \;=\; n \cdot \lceil \log_2 n \rceil + L_\phi,
  \qquad L_\phi \;\ge\; n \log_2 e - O(\log n),
\end{equation}
and dividing by $n$, with $c_\phi = L_\phi / n$ the addressing cost per
element,
\begin{equation}
\label{eq:bphf-per-element}
  L_{\text{BPHF}} / n
  \;=\; \lceil \log_2 n \rceil + c_\phi,
  \qquad c_\phi \;\ge\; \log_2 e - o(1).
\end{equation}

\begin{proposition}[BPHF space]
\label{prop:bphf-space}
The Bernoulli Perfect Hash Filter of \Cref{def:bphf} on a designated set
$A$ with $|A| = n$ uses
\[
  L_{\text{BPHF}} / n
  \;=\; \lceil \log_2 n \rceil + c_\phi
  \;=\; \log_2 n + O(1)
\]
bits per element, where $c_\phi \ge \log_2 e - o(1)$ is the bits per key
of the minimal perfect hash.
\end{proposition}

The proposition has the form of \Cref{prop:phf-space} with one
difference: the leading term is controlled by the set size $n$, not the
target rate $\fprate$. The two budgets
\[
  L_{\text{PHF}} / n = \lceil -\log_2 \fprate \rceil + c_\phi,
  \qquad
  L_{\text{BPHF}} / n = \lceil \log_2 n \rceil + c_\phi
\]
share the addressing term and differ in the slot width. The perfect hash
filter spends slot bits at a rate the designer sets through $\fprate$;
the BPHF at a rate the set size dictates. The perfect hash filter pays
$\lceil -\log_2 \fprate \rceil$ bits per slot to make a false-positive
coincidence rare; the BPHF pays $\lceil \log_2 n \rceil$ bits per slot so
the rank assignment can name all $n$ members apart and certify a witness.
At full resolution the BPHF is exact (the $\fnrate = 0$ corner); the
$k$-perfect dial of \Cref{sec:bphf-construction} shrinks the slot count
to $m < n$ and trades $\fnrate \ge 1 - m/n$ for the saved space.

\subsection*{Build and query time}

The build writes one rank per element in a one-pass $O(n)$ stage plus the
expected-$O(n)$ minimal perfect hash construction of
\Cref{sec:construction-time}, dominated by the latter; build throughputs
match the perfect hash filter's. The rank fill is embarrassingly parallel
(distinct slots by bijectivity), running after the perfect-hash stage.
The only build-time difference from the perfect hash filter is computing
a rank $\rho(a)$ rather than a fingerprint $g(a)$ per element, both
$O(1)$, though computing the ranks themselves may require a sort.

The query of \Cref{alg:bphf-build-query} runs in $O(1)$: one
perfect-hash evaluation, one rank evaluation, one memory read, and an
$r$-bit comparison (at machine-word speed for any $n$ up to $2^{64}$).
The cycle count is essentially the perfect hash filter's, differing
only in which function is the second evaluation and what the table read
returns.

\subsection*{The bit-cost picture at \texorpdfstring{$n = 10^6$}{n = 10\^{}6}}

Fix $n = 10^6$. The BPHF's slot width is $\lceil \log_2 10^6 \rceil = 20$
bits, independent of any error target; the perfect hash filter's is
$\lceil -\log_2 \fprate \rceil$. \Cref{tab:bhf-bphf-bits} puts them side
by side; both add the same addressing cost $c_\phi$.

\begin{table}[h]
\centering

\rceil = 20$ (\Cref{prop:bphf-space}), constant since the BPHF guarantees

The two filters cross over at $\fprate = 1/n$, where $\lceil -\log_2
\fprate \rceil = \lceil \log_2 n \rceil$: at $n = 10^6$ this is $\fprate =
2^{-20} \approx 10^{-6}$. Above the crossover (looser targets, $\fprate >
1/n$) the perfect hash filter is cheaper; below it (stricter targets)
the BPHF is cheaper at the same $n$. The two regimes are the two
operating modes, the perfect hash filter where the application tolerates
some false positives for cheap storage, the BPHF where it cannot
tolerate any and the witness model holds. The BPHF's extra bits in the
loose-target regime are not wasted: they buy a guarantee that no
fingerprint width delivers. A perfect hash filter at $\fprate =
10^{-2}$ admits about one false positive per hundred non-member queries;
a BPHF at the same $n$ admits none from candidates without a valid
rank. The $13$ extra
bits per element are the price of converting a $10^{-2}$ probability into
a certainty on the consequential axis, the conversion
\Cref{sec:ranked-search} shows paying for itself in top-$k$ retrieval.
