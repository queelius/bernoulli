\section{Space and Time Analysis}
\label{sec:space-time-analysis}

\Cref{sec:bphf-construction} fixed the BPHF's two storage objects:
the perfect hash $\phi$ and the rank table $R$ of width $r =
\lceil \log_2 n \rceil$ from \eqref{eq:bphf-r}. The present section
accounts for the bits each contributes, totals the cost per element,
and gives the build and query times the construction inherits from
its chapter~14 ancestor. The headline result is a proposition that
the BPHF's per-element bit cost is $\lceil \log_2 n \rceil + o(1)$ as
$n$ grows, with the perfect-hash overhead vanishing in the same way
\Cref{sec:space-analysis} documented for the BHF. The build runs in
expected $O(n)$ time and queries run in $O(1)$ time, matching the
BHF's performance profile on the time axes. The structural difference
lies on the space axis: the BPHF's bits-per-element depends on the
set size $n$, while the BHF's depends on the target error rate
$\fprate$. The two families are not substitutes parameter-for-
parameter; they trade different quantities for different guarantees,
and the table at the end of the section makes the trade concrete at
a million elements.

\subsection*{Rank table storage}

The rank table $R : [n] \to \{0, 1\}^r$ holds $n$ slots, each of
width $r$ bits. The total bit cost is
\begin{equation}
\label{eq:bphf-rank-bits}
  L_R \;=\; n \cdot r \;=\; n \cdot \lceil \log_2 n \rceil
\end{equation}
bits. The dependence on the set size is doubly linear in the sense
that the slot count is $n$ and the per-slot width grows as $\log_2 n$.
At $n = 1000$ the table costs $10{,}000$ bits ($r = 10$, computed in
\Cref{sec:bphf-construction}). At $n = 10^6$ the table costs $20
\cdot 10^6 = 2 \cdot 10^7$ bits, or about $2.5$ megabytes. At
$n = 10^9$ the table costs $30 \cdot 10^9 = 3 \cdot 10^{10}$ bits, or
about $3.75$ gigabytes. The growth rate is $n \log_2 n$, the same
information-theoretic cost a fully sorted lookup index pays to
distinguish $n$ ranks from one another.

The integer rounding in $r = \lceil \log_2 n \rceil$ contributes
between $0$ and $1$ extra bits per element compared to the
real-valued $\log_2 n$. When $n$ is exactly a power of two the
rounding is zero; in the worst case it approaches one bit per
element. Over a uniformly distributed $n$ on a logarithmic scale the
rounding averages $0.5$ bits per element, the same rounding profile
the BHF showed in \Cref{sec:space-analysis}. The rounding cost is
small in absolute terms and well-understood; the chapter does not
pursue fractional-bit rank encodings because the gains are not worth
the query-time complexity, the same conclusion chapter~14 reached
for fingerprints.

The rank table is the densest possible representation of a uniform
rank per element. Each slot holds exactly $r$ bits, the minimum
needed to distinguish $n$ ranks. The table has exactly $n$ slots,
the minimum needed to address every element of $A$ through the
perfect hash $\phi$. There is no padding, no per-slot overhead, and
no addressing structure inside the table other than the indexing by
$\phi$. The table is a flat array, addressed deterministically, and
the bit cost is the sum of the per-slot widths.

\subsection*{Perfect-hash storage}

The second storage object is the perfect hash $\phi$ itself.
\Cref{sec:space-analysis} computed the BHF's perfect-hash overhead
in detail; the BPHF inherits the same machinery without modification,
because the perfect-hash construction depends on the set $A$ alone
and not on what gets stored at each slot. The asymptotic bound from
the Belazzougui-Botelho-Dietzfelbinger family is
\[
  L_\phi \;=\; O\bigl( n \log \log \log n / \log n \bigr)
\]
bits, which is $o(n)$ and therefore vanishing relative to the rank
table's $n \log_2 n$. The per-element overhead $L_\phi / n =
O(\log \log \log n / \log n)$ tends to zero as $n$ grows. At $n = 10^6$
practical implementations report between $2$ and $3$ bits per
element; at $n = 10^9$ the figure drops to between $1.5$ and $2.5$
bits per element. The full discussion is in chapter~14; the BPHF
inherits both the asymptotic bound and the practical constants
unchanged.

The structural reason the BPHF and BHF share their perfect-hash
overhead is that the perfect hash is a property of the set, not of
the values stored at each slot. The chapter~14 build pass populated
$F[\phi(a)] = g(a)$ with the fingerprint $g(a)$; the chapter~15 build
pass populates $R[\phi(a)] = \rho(a)$ with the rank $\rho(a)$. The
only changed component is the per-slot value. The perfect-hash
representation, the slot count, and the addressing pattern are
identical. Whatever bound holds for the BHF's $\phi$ holds for the
BPHF's $\phi$ as well, and the chapter does not redo the derivation.

\subsection*{Total bits per element}

Combining the two terms,
\begin{equation}
\label{eq:bphf-total-bits}
  L_{\text{BPHF}}
  \;=\; L_R + L_\phi
  \;=\; n \cdot \lceil \log_2 n \rceil
  \;+\; O\bigl( n \log \log \log n / \log n \bigr)
\end{equation}
bits. Dividing by $n$,
\begin{equation}
\label{eq:bphf-per-element}
  L_{\text{BPHF}} / n
  \;=\; \lceil \log_2 n \rceil
  \;+\; O(\log \log \log n / \log n).
\end{equation}
The first term is bounded between $\log_2 n$ and $\log_2 n + 1$ by
integer rounding. The second term is $o(1)$ as $n \to \infty$. The
per-element bit cost approaches the integer rounding of $\log_2 n$,
with the perfect-hash correction vanishing in the limit.

\begin{proposition}[BPHF space]
\label{prop:bphf-space}
The Bernoulli Perfect Hash Filter of \Cref{def:bphf} on a
designated set $A$ with $|A| = n$ uses
\[
  L_{\text{BPHF}} / n
  \;=\; \lceil \log_2 n \rceil
  \;+\; o(1)
  \;=\; \log_2 n \;+\; O(1)
\]
bits per element. The dominant term is the rank table at $\lceil
\log_2 n \rceil$ bits per element; the perfect-hash overhead is a
sublinear additive correction that vanishes as $n \to \infty$.
\end{proposition}

The proposition has the same form as \Cref{thm:bhf-optimality} for
the BHF, with one key difference: the parameter controlling the
leading term is the set size $n$, not the target rate $\fprate$. The
two formulas
\[
  L_{\text{BHF}} / n
    \;=\; \lceil -\log_2 \fprate \rceil + o(1),
  \qquad
  L_{\text{BPHF}} / n
    \;=\; \lceil \log_2 n \rceil + o(1)
\]
are functions of different inputs. The BHF spends bits at a rate the
designer chooses through the target $\fprate$; the BPHF spends bits
at a rate the application's set size dictates. At small $n$ the BPHF
is cheaper per element than a BHF at any nontrivial $\fprate$; at
large $n$ the BPHF becomes more expensive than a BHF at any but the
strictest $\fprate$ targets. The crossover is computed concretely in
the comparison table below.

The asymmetry is not a defect of one construction relative to the
other. The two filters give different guarantees, and the bit costs
reflect what each guarantee requires. The BHF guarantees $\fnrate =
0$ at the cost of $\fprate \le 2^{-r}$, and pays $r = \lceil -\log_2
\fprate \rceil$ bits per element to make the false-positive
probability small enough. The BPHF guarantees $\fprate = 0$ in the
witness query model and pays $r = \lceil \log_2 n \rceil$ bits per
element so the rank assignment can name all $n$ elements apart. At
full resolution with a true perfect hash the BPHF is exact (the
$\fnrate = 0$ corner of the perfect-filter line); the per-element
budget of \Cref{prop:bphf-space} is the cost of that exact corner.
The dial that buys a smaller table is the $k$-perfect hash of
\Cref{sec:bphf-construction}, which shrinks the slot count to $m < n$
and trades a controlled $\fnrate \approx 1 - m/n$ for the saved
space. Each construction's bit budget is the minimum needed for its
guarantee, and each spends extra bits, on its own axis, only to drive
the controlled error rate down.

\subsection*{Build time}

The build pass of \eqref{eq:bphf-build} writes one rank value per
element, plus the perfect-hash construction itself. The
fingerprint-fill stage of the BHF was a one-pass operation in $O(n)$
time; the rank-fill stage of the BPHF is identical at the algorithmic
level. The perfect-hash construction is the same expected-$O(n)$
subroutine \Cref{sec:construction-time} described for the BHF, with
the same family of candidate algorithms (Fredman-Komlos-Szemeredi,
Hagerup-Tholey, the displacement-based MWHC and BBHash, and the
modern Belazzougui-Botelho-Dietzfelbinger scheme). The expected total
build time is therefore $O(n)$, dominated by the perfect-hash
construction.

The BPHF inherits the chapter~14 implementation lineage without
modification: build throughputs on the order of $10$ to $50$ million
elements per second on commodity hardware, end-to-end build times on
the order of seconds for million-element sets and minutes for
billion-element sets. The rank-fill pass is embarrassingly parallel
(each iteration writes a distinct slot, since $\phi$ is a bijection
on $A$), and the perfect-hash construction admits parallel variants
in the published implementations. The two-stage pipeline
(perfect-hash first, ranks second) runs sequentially at the stage
level but parallel within each stage, matching the chapter~14
organization.

The only build-time difference between the BHF and the BPHF is the
nature of the per-slot value being computed. The BHF computes a
fingerprint hash $g(a)$ per element; the BPHF computes a rank
$\rho(a)$ per element. Both are $O(1)$ per element. The total
per-element build cost is the same constant-time evaluation plus the
$O(1)$ amortized share of the perfect-hash construction. The two
constructions differ in what they store, not in how much work each
storage operation costs.

\subsection*{Query time}

The query algorithm of \Cref{alg:bphf-build-query} runs in $O(1)$
time. It evaluates the perfect hash $\phi(x)$ once (one
constant-time data-structure lookup), evaluates the rank function
$\rho(x)$ once (one hash or one metadata lookup), reads one $r$-bit
slot of the table (one memory access), and compares two $r$-bit
strings (constant time when $r$ fits in a machine word, which it
does for any $n$ up to $2^{64}$ on a $64$-bit architecture). The
total work is constant in $n$ and constant in the universe size,
dominated by the two function evaluations and the one memory read.

Compared to the BHF's query cost, the BPHF performs the same two
function evaluations and the same one memory read; the only
difference is which function is the second one ($\rho$ rather than
$g$) and what value comes back from the table read (a rank rather
than a fingerprint). The cycle count is essentially identical. The
$r$-bit comparison is at machine-word speed in both constructions.
The two filters share their query-time profile to within constant
factors that depend on whichever specific perfect-hash family is in
use.

\subsection*{The bit-cost picture at \texorpdfstring{$n = 10^6$}{n = 10\^{}6}}

Fix $n = 10^6$ elements and compare the BHF and BPHF bit budgets.
The BHF's per-element cost is $\lceil -\log_2 \fprate \rceil$, which
depends on the target $\fprate$. The BPHF's per-element cost is
$\lceil \log_2 n \rceil = \lceil \log_2 10^6 \rceil = \lceil
19.93 \rceil = 20$ bits, independent of any error target.
\Cref{tab:bhf-bphf-bits} reports the BHF cost at three target rates
and the BPHF cost (constant across the table).

\begin{table}[h]
\centering
\caption{Bits per element at $n = 10^6$. BHF column is $\lceil -\log_2
\fprate \rceil$ from \Cref{thm:bhf-optimality}; BPHF column is
$\lceil \log_2 n \rceil = 20$ from \Cref{prop:bphf-space}, independent
of $\fprate$ since the BPHF guarantees $\fprate = 0$ exactly. Both
columns omit the sublinear perfect-hash overhead.}
\label{tab:bhf-bphf-bits}
\begin{tabular}{l|cc}
\hline
  $\fprate$  & BHF & BPHF \\
\hline
  $10^{-2}$  & $7$  & $20$ \\
  $10^{-3}$  & $10$ & $20$ \\
  $10^{-6}$  & $20$ & $20$ \\
\hline
\end{tabular}
\end{table}

At $\fprate = 10^{-2}$ the BHF spends $7$ bits per element and the
BPHF spends $20$, a factor of $2.86$ more expensive on the bit axis.
At $\fprate = 10^{-3}$ the BHF spends $10$ bits per element and the
BPHF spends $20$, a factor of $2$ more expensive. At $\fprate =
10^{-6}$ the two filters cross over and tie at $20$ bits per element.
For any target stricter than $\fprate = 10^{-6}$ at $n = 10^6$, the
BPHF is actually cheaper than the BHF at the same set size; for any
target looser than $\fprate = 10^{-6}$, the BHF is cheaper.

The crossover point at $n = 10^6$ is $\fprate = 2^{-20} \approx
10^{-6}$, where the two formulas give the same bit count. In general
the crossover is at $\fprate = 1/n$: setting $\lceil -\log_2 \fprate
\rceil = \lceil \log_2 n \rceil$ gives $\fprate = 1/n$. Below the
crossover (stricter targets, equivalently $\fprate < 1/n$) the BPHF
is the cheaper construction at the same $n$. Above the crossover
(looser targets, $\fprate > 1/n$) the BHF is the cheaper
construction. The two regimes correspond to the two operational
modes: the BHF is the right tool when the application tolerates
some false positives in exchange for cheap storage; the BPHF is the
right tool when the application cannot tolerate any false positives
at all, and pays the extra bits to enforce $\fprate = 0$.

The BPHF's extra bits in the loose-target regime are not wasted;
they buy a guarantee that the BHF cannot deliver at any bit budget.
A BHF at $\fprate = 10^{-2}$ admits roughly one false positive per
hundred non-member queries, regardless of how many bits are spent
beyond the entropy floor. A BPHF at the same $n = 10^6$ admits zero
false positives, period. The $13$ extra bits per element (over the
BHF at $\fprate = 10^{-2}$) are the price of converting a $10^{-2}$
probability into a $0$ certainty on the consequential axis. The
\Cref{sec:ranked-search} application discussion works through one
setting where the conversion pays for itself: top-$k$ retrieval,
where a false positive surfaces an off-topic document as if it
belonged in the top set, and the application's precision invariant
is the $\fprate = 0$ guarantee the BPHF provides.
