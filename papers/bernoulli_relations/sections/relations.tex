\section{Relations, queries, and source identity}
\label{sec:relations}
We use finite relations with set semantics, following the relational
model~\cite{codd1970}. There are no duplicate rows, null values, or approximate
comparisons of attribute values. A schema $A$ assigns each named attribute
$a\in A$ a finite domain $D_a$; its tuple universe is
$U_A=\prod_{a\in A}D_a$. A relation $\Relation{R}$ is a subset of $U_A$.
We write $t|_B$ for restriction of a tuple to attributes $B\subseteq A$.

For a deterministic predicate $P$ and $B\subseteq A$, selection and projection are
\[
 \sigma_P(\Relation{R})=\{t\in\Relation{R}:P(t)\},\qquad
 \pi_B(\Relation{R})=\{t|_B:t\in\Relation{R}\}.
\]
If $\Relation{S}$ has schema $C$, natural join is
\[
 \Relation{R}\Join\Relation{S}
 =\{t\in U_{A\cup C}:t|_A\in\Relation{R},\ t|_C\in\Relation{S}\}.
\]
Binary relational composition is the existential join
$(\Relation{R};\Relation{S})(x,z)=\bigvee_y
 [\Relation{R}(x,y)\land\Relation{S}(y,z)]$.
These definitions fix the candidate universe even when an implementation
answers membership probes without enumerating the relation.

A fixed answer to a positive query built from selection, projection, join,
and union has a monotone Boolean \emph{lineage}: conjunction combines the
facts needed for a witness, and disjunction combines alternative witnesses.
This is established provenance machinery~\cite{green2007provenance,suciu2011}.
The relevant variables name distinct stored random outcomes. Reusing a tuple,
reusing a relation, or evaluating the same membership probe twice does not
create a fresh variable.

For example, a symmetry-preserving representation may answer both
$R(u,v)$ and $R(v,u)$ using the same bit $X_{\{u,v\}}$. Then the query
$R(u,v)\land R(v,u)$ has lineage $X_{\{u,v\}}$, not a conjunction of
independent bits. More generally a family of binary witnesses gives
\[
 F_G(X)=\bigvee_{\{i,j\}\in E(G)}(X_i\land X_j).
\]
The graph records reuse between witnesses. Paths and cycles of witnesses
will provide a tractable query class in \cref{sec:query_contracts}.
The restriction concerns lineage after identifying aliases, not merely the
number of occurrences in the query text. Negation and arbitrary aggregates
are outside the contract results below.
